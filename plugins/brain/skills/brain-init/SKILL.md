# brain-init

Idempotent setup. Safe to re-run. Helpers live in `${CLAUDE_PLUGIN_ROOT}/scripts/brain_bootstrap.py`.

The plugin provides the session-start hook, so `wire_settings(parent)` never registers one. Tell the user the hook is supplied by the plugin. `wire_settings` sets `CLAUDE_VAULT` and disables native auto-memory.

There are two layouts:
- **Solo**: one vault in one git repository, for one person who keeps everything in one place. It is stored as `privateVault` in the config, and `personalVault` and `sharedTree` stay unset. The remote is optional. A vault with no remote is saved by local commits only.
- **Tiered**: a personal work repository (`personalVault`), a shared team repository (`sharedTree`), and an optional private repository for non-work knowledge (`privateVault`). The three are siblings under one parent, which is the Obsidian vault root, so cross-repo wikilinks resolve.

## 0. Preflight (before any `uv run`)
Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/preflight.sh"` with the source flags the user enables (`gh`, `gitea`, `cloudflare`), then re-run after step 2 once sources are chosen. If it exits non-zero, show its guidance for installing `uv`, `git`, and any enabled `gh` or `tea`, then stop until the user installs the missing tools. Everything below depends on `uv`, and users often assume any Python will do, so never skip this.

## 1. Detect
Read `~/.config/brain/config.json` (or the file named by `$BRAIN_CONFIG`) via `brain_lib.load_config`. It is complete when at least one root and `journalsDir` are set. If present and complete, first check `wiring.launchdWeekly`. When it is true, call `install_launchd(vault_path=<parent of the configured roots, or the solo vault>)` before you report anything, then tell the user the weekly agent was refreshed from the installed plugin version. The wrapper and plist come from the plugin, so a plain re-run is the only way an existing install gets a newer one. When it is false or declined, make no call. Then report the current config and ask what to change. If absent or incomplete, run the full bootstrap below.

## 2. Ask (defaults in brackets)
- Layout: solo or tiered [solo]. Explain the difference in one sentence each, as above. Someone setting up a brain for themselves at home wants solo. Tiered is for a team that shares a brain repository.
- Solo vault path [`${HOME}/brain`]. Remote, optional. A remote must already exist, brain-init does not create it. When the path does not exist yet and a remote is given, the remote is cloned. Without a remote, tell the user plainly that the vault lives only on this machine, and suggest a backup such as Time Machine. Solo tree defaults are `wiki-me/projects` and `wiki-me/life`. The user can rename `me` or add trees.
- Tiered only: personal vault path [`${HOME}/brain/personal`] and its remote. The personal repository must already exist on the remote for a push to succeed. brain-init does not create it.
- Tiered only: shared repo URL for the user's team, cloned to [`${HOME}/brain/shared`]. A new shared brain repository must use `master` as its default branch. Each team member contributes from their own userid branch, and pull requests target `master`.
- Tiered only: private repository, optional. Ask whether the user wants a third repository for non-work knowledge, such as side projects and personal life. Explain why: the personal and shared repositories live on work infrastructure, so anything non-work there sits in work git history for good. A private repository keeps that material on a remote of the user's own and can be cloned on its own on a non-work machine, as a solo vault. Default path [`${HOME}/brain/private`], a sibling of `personal` and `shared`. Refuse a remote on the same host as the personal or shared repository, because that defeats the purpose. The user can also keep it local with no remote. Its git identity is the user's private name and email, never the work email. Private tree defaults are `projects` and `life`. A no is a valid answer. Record it as `"privateVault": {"declined": true}` so the question is not repeated.
- Tiered only: personal tree defaults are `wiki-me` and `life`. With a private repository the default is `wiki-me` only, because `life` belongs in the private repository. The shared tree default is `wiki-team`. It must match the tree their team's shared repository already uses.
- Git identity for each brain repository. Ask which display name and email to use. Propose each repository's existing local values when present. Otherwise propose the local account name and an email the user confirms. Explain why this is required: identity is configured per repository, so the right author lands in the history, and a wrong author on a shared repository is hard to correct after it is pushed. Never set global git config.
- Journals dir [`${HOME}/private/projects`].
- Which freshness sources they have: git, gh, gitea, cloudflare. Only git is on by default.
- Weekly maintenance agent. First read the config if it exists. If `wiring.launchdWeekly` is already set, tell the user whether weekly maintenance is currently opted in or declined and preserve that choice unless they explicitly ask to change it. If it is not set, ask whether to enable it, defaulting to no. Explain that the weekly run rebuilds the catalogs, then executes `/brain-lint --fix` and `/brain-digest`, which write to the vault. With a shared repository configured it also pulls shared knowledge, and those commands write shared vault content that affects the whole team, so normally one designated person per team enables it and everyone else declines.

## 3. Apply (call the helpers, in order)
Run each via `uv run "${CLAUDE_PLUGIN_ROOT}/scripts/brain_bootstrap.py" <fn> ...` using the dispatcher, or use inline `uv run python -c`. In solo mode, steps 1 to 3 do not apply. Go to step 4, which sets up the solo vault as the private repository.
1. Tiered: `scaffold_vault(personal, ["wiki-me","life"], template="${CLAUDE_PLUGIN_ROOT}/templates/vault-CLAUDE.md")`. Pass the personal tree list as JSON to the dispatcher. Include any extra personal tree names chosen in step 2, and drop `life` when the user chose a private repository. `scaffold_vault` initializes the repository and ignores its generated `index.md` and `MUSTKNOW.md` catalogs. It writes `CLAUDE.md` only into a new vault. When `personal/CLAUDE.md` already exists and differs from the template, show the user the difference and ask before writing anything. If the file is otherwise the template, replace it with the template. If it is customised, for example with its own tree layout, update only the lines that describe the brain's own machinery, such as the generated files, how a page is found and what the hook injects, so they match the template. Keep the user's tree layout and any other local content. The file is tracked in the personal repository, so either change is recoverable with git. Then run `git -C <personal> config user.name <confirmed-personal-name>` and `git -C <personal> config user.email <confirmed-personal-email>`. These are repository-local settings.
2. Tiered: if the user supplied a personal remote, configure backup from the personal vault repository. If no `origin` exists, run plain `git remote add origin <personal-remote>`. Leave an existing origin alone rather than rewriting it. If the repository has no commits, make the initial commit. Then push with `git push -u origin <branch>`. Skip this entire step when no personal remote was given.
3. Tiered: `git clone <shared repo>` into the shared path. Skip this if it already exists, then use `git pull` instead. Its `wiki-team` tree must match the team repository. Then run `git -C <shared> config user.name <confirmed-shared-name>` and `git -C <shared> config user.email <confirmed-shared-email>`. This also repairs existing repositories that have no local identity.
4. The solo vault, or the tiered private repository when the user wants one:
   - When a remote was given and the path does not exist yet, try `git clone <remote> <path>` first. The user may already have the vault from another machine. A clone of an empty remote is fine.
   - Otherwise call `scaffold_vault(<path>, <trees>, template="${CLAUDE_PLUGIN_ROOT}/templates/vault-CLAUDE.md")` with the trees chosen in step 2. Then, when a remote was given and no `origin` exists, add it as `origin`, make the initial commit if there is none, and push with `git push -u origin <branch>`. Without a remote, make the initial commit and stop there.
   - Run `git -C <path> config user.name <confirmed-name>` and `git -C <path> config user.email <confirmed-email>`.
   - Tiered only, non-work trees: when you add a private repository, move the non-work trees into it. If the personal repository holds trees such as `life/` or a side-projects tree, list them and ask whether to move them. Read a page's body before you classify it, never decide by title. On a yes, copy the trees into the private repository, give each wiki folder a gloss in the private `topics.yaml`, remove them from the personal repository, and save both repositories. Also offer to move non-work entries out of the personal `log.md` and `digests/`. Tell the user plainly that the personal repository's git history still holds the moved content. Rewriting that history is the user's decision, never automatic.
5. Compute `parent`: the solo vault itself, or in tiered mode the common parent of the sibling `personal`, `shared` and, when present, `private` repositories. Call `wire_settings(parent)` to set CLAUDE_VAULT and disable native auto-memory. It registers no hook, because the plugin provides the session-start hook.
6. `install_feed_rules(journalsDir)` into `~/.claude/CLAUDE.md`, then create the journals directory. A `CLAUDE.md` without feed markers that already describes the vault gets no second copy: the call writes nothing and returns `{"existing": [...]}` with the lines it found. Show the user those lines and ask. Keeping the hand-written text means later plugin updates never change it. Appending the managed block keeps it current, and the hand-written copy should then go. Only after an explicit yes, call `install_feed_rules(journalsDir, true)`.
7. Call `install_launchd(vault_path=parent)` to install the weekly agent when the user says yes to weekly maintenance now, or when `wiring.launchdWeekly` is already true and they did not ask to change it. The wrapper and plist come from the installed plugin version, so a re-run refreshes them and reloads the agent. Its log directory defaults to `~/.config/brain`. When they decline, do not call `install_launchd`.
8. `write_config({...})`. Solo writes only `privateVault`:
   ```
   {"version": 1,
    "privateVault": {"path": "<vault path>", "remote": "<remote or null>"},
    "journalsDir": "<journalsDir>",
    "freshnessSources": {"git": true, "gh": false, "gitea": false, "cloudflare": false},
    "wiring": {"launchdWeekly": false}}
   ```
   Tiered writes `personalVault`, `sharedTree` (with `"prWorkflow": true`) and always a `privateVault` key: `{"path": ..., "remote": ...}` when the user has a private repository, `{"declined": true}` when they said no. Include `"wiring": {"launchdWeekly": true}` only when weekly maintenance is opted in. On a re-run, retain the existing `wiring.launchdWeekly` value unless the user explicitly changes their choice.
9. `brain_lib.py rebuild` to seed index.md and MUSTKNOW.md across all configured roots. This is mandatory after a clone or a scaffold because the catalogs are gitignored, so a fresh clone has none.

## 4. Report transparently
Tell the user plainly that native auto-memory is now OFF (`autoMemoryEnabled: false`) and the vault is the memory instead. If weekly maintenance was opted in, tell them that macOS will show a background activity notification named `brain-maintenance`. It is the weekly vault maintenance job. A launchd agent runs it every Monday at 08:00. Run `launchctl start com.github.arnemoor.brain.vault-maintenance` to run it now. To remove it, run `launchctl unload ~/Library/LaunchAgents/com.github.arnemoor.brain.vault-maintenance.plist` and delete that plist. If weekly maintenance was declined, say plainly that no background item is registered and that they can enable it later by re-running `/brain-init`. List the layout, the vault paths, each remote or that there is none, and the enabled freshness sources. Never print secrets.

## Git workflow
Solo, personal and private changes auto-commit after a writing skill completes and push to their own remote when one is set. Shared changes go through `/brain-contribute` as a pull request. At session start the plugin syncs every root except the shared tree with its remote, at most once an hour. Pull and reindex shared knowledge on demand through `/brain-sync`.

## Voice + secrets
No em dash, en dash, or semicolon in anything you author. Never write a token or credential into the config or the vault.
